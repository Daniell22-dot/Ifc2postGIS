# Architecture

This document describes how the ifc2postgis converter is structured and
how data flows from an IFC file into a PostGIS database.

## Overview

The converter is a Python package that exposes a single command line
entry point. The CLI reads user options, the parser walks the IFC file
and extracts geometry and attributes, and the database module owns all
SQL and connection handling.

## Package layout

    ifc2postgis/
        __init__.py     Package metadata
        cli.py          Click command, argument validation
        parser.py       IFC traversal and geometry extraction
        database.py     Connection, schema creation, inserts

## Data flow

1. The user invokes the CLI with an input file, a database URL, and an
   optional SRID and schema name.

2. cli.py validates the options and calls parser.process_ifc.

3. process_ifc opens the IFC file with IfcOpenShell and builds a
   geometry settings object configured for world coordinates.

4. process_ifc calls database.create_schema to prepare the four target
   tables. By default existing tables are dropped first.

5. For each IfcSite, IfcBuilding, IfcBuildingStorey, and IfcSpace in the
   file, process_ifc extracts the GlobalId, name, parent link, and a WKT
   geometry string, then calls the matching insert function.

6. database.py executes the inserts. Geometry is built with
   ST_GeomFromText so the SRID is attached at insert time.

7. On success process_ifc commits. On any exception it rolls back and
   the CLI exits with a non-zero status.

## Spatial hierarchy resolution

The IFC schema allows objects to be related to their parent in more
than one way. The converter resolves parents through
ifcopenshell.util.element.get_aggregate, which follows
IfcRelAggregates relationships. This covers the common case where
sites aggregate buildings, buildings aggregate storeys, and storeys
aggregate spaces.

If a file uses IfcRelContainedInSpatialStructure instead, the parent
link will be null. A future revision should fall back to a manual
traversal of the relationship entities.

## Geometry extraction

Geometry is generated by ifcopenshell.geom.create_shape with the
use-world-coords setting enabled. Vertices are therefore already
positioned relative to the IFC project origin and do not need further
transformation.

The current version emits MULTIPOINT Z geometry built from the vertex
buffer. This preserves exact 3D coordinates but discards face
connectivity. A later revision should reconstruct surface geometry
from the face index buffer and emit either TIN Z or POLYHEDRALSURFACE Z
so that PostGIS can compute area and volume.

## Error handling

A geometry failure on a single element returns None and the element is
inserted with a null geometry column. This prevents one malformed
element from aborting the whole conversion.

Any other error propagates to the CLI, which prints the message and
exits with a non-zero status. The database transaction is rolled back
in that case.

## Extending the converter

To add a new output table:

1. Add a CREATE TABLE statement in database.create_schema.
2. Add an insert helper in database.py.
3. Call the helper from parser.process_ifc for the relevant IFC type.

To support new IFC versions or new geometry representations, modify
only parser.py. The CLI and database modules do not depend on the IFC
schema details.
